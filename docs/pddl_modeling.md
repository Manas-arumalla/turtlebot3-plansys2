# PDDL Modelling Notes

Two domains model the same missions at different levels of fidelity. This page walks
through both and records the modelling decisions — most of which I got wrong at least
once before landing here.

## The STRIPS domain (`domain_strips.pddl`)

The minimal classical model: what must be true for the mission to make sense, and
nothing else.

```pddl
(:action move
  :parameters (?r - robot ?from - location ?to - location)
  :precondition (and (robot_at ?r ?from) (connected ?from ?to))
  :effect (and (not (robot_at ?r ?from)) (robot_at ?r ?to)))

(:action clean
  :parameters (?r - robot ?l - location)
  :precondition (and (robot_at ?r ?l) (dirty ?l))
  :effect (and (not (dirty ?l)) (cleaned ?l)))
```

### Decisions worth recording

**`connected` is directed, and problems declare both directions explicitly.** It
costs a few lines per problem file (the problem builder emits them automatically at
runtime) and buys a capability: after a navigation failure the executor can block
`hall → commode` without touching `commode → hall`. It also makes `connected` a
*static* predicate — no action changes it — which the internal planner exploits by
resolving connectivity once at grounding time. Grounding produces one `move` per
declared edge instead of one per location pair: 10 ground moves for the washroom, not
25.

**`clean` requires `(dirty ?l)`.** The first version omitted this; plans were still
"optimal" but the model allowed cleaning any location any number of times, which
bloats the search space and hides modelling errors. Requiring dirt makes `clean`
consume a resource — each goal is achievable exactly one way, and a double-clean is a
validation error rather than a silent no-op.

**`cleaned` and `dirty` are separate predicates, not one negated atom.** Goals stay
positive (`(cleaned basin)`), which keeps the problem inside the fragment every
planner handles well, and locations that are neither dirty nor cleaned (plain
waypoints like `hall`) are representable.

**No `dock`/battery in STRIPS.** Charge management is inherently numeric-temporal;
faking it with predicates (battery-level buckets) makes plans ugly and teaches the
wrong lesson. STRIPS mode is for *ordering* decisions; energy lives in the temporal
domain.

## The temporal domain (`domain_temporal.pddl`)

PDDL 2.1 with `:durative-actions` and `:fluents`, solved by POPF:

- `move` takes `(travel-time ?from ?to)` seconds — the problem builder computes real
  values from waypoint geometry and the robot's nominal speed — and drains
  `(travel-drain ?from ?to)` battery at the end.
- `clean` and `deep_clean` are separate durative actions gated by `dirty` /
  `deep_dirty`, with per-fixture durations from the world model.
- `recharge` requires the robot to sit at a `charger_at` location and *assigns*
  battery to 100 at the end — modelling a full charge cycle rather than incremental
  charging, which POPF handles much more robustly than continuous effects.
- Battery preconditions are `at start` checks: an action may not begin unless the
  budget covers it. Combined with `(:metric minimize (total-time))`, POPF inserts
  recharges only when needed and as late as possible.

`washroom_small_temporal.pddl` is tuned so the recharge is *forced*: 18% starting
battery cannot cover both fixtures on any route. If you edit the numbers and the
recharge disappears from the plan, that is the planner being right, not a bug.

### Timing conventions that matter

- `move` releases `(robot_at ?r ?from)` **at start** and grants the destination
  **at end** — the robot is nowhere during transit, so nothing can overlap with it.
- `clean` requires `(over all (robot_at ?r ?l))` — the robot must *stay* during the
  whole action. This is the constraint that makes "start cleaning, drive away
  mid-clean" unplannable.

## Runtime problem generation

Hand-written problem files (`pddl/problems/`) exist for demos and tests, but during a
mission every problem is generated by `problem_builder.py` from a `WorldSnapshot`:

```
robot_at      <- world.robot_at        (updated as moves succeed)
connected     <- world.edges - world.blocked
dirty/cleaned <- fixture states        (updated as cleans succeed)
battery, travel-time, clean-time ...   (temporal mode)
goal          <- remaining mission goals only
```

Replanning after a failure is therefore *identical* to initial planning — there is no
special "repair" path, no second code path to test, and the problem can never drift
from the world model because it is derived from it.

One asymmetry is handled explicitly: `deep_dirty` fixtures have no `deep_clean`
action in STRIPS mode, so the engine folds them into `dirty` when building STRIPS
problems. In temporal mode they stay separate and cost more time.

## Validation as a habit

`washbot_planning.pddl_core.validator` replays any plan through the domain:
preconditions checked per step, effects applied, goal checked at the end. It runs

1. in the executor, before any plan is dispatched,
2. in the benchmark harness, so a "solved" row means a *correct* plan,
3. in the test suite, pinning both domains to their intended semantics
   (e.g. `test_double_clean_rejected`).

The internal parser deliberately **refuses** anything outside its fragment —
durative actions, `:functions`, quantifiers, negative preconditions — with an error
naming the backend that can handle it. A planner that silently approximates
semantics is worse than no planner.

## Scaling shape (for the benchmarks)

The generator (`generator.py`) builds corridor-spine facilities: `dock —
corridor_1 — corridor_2 — …` with rooms hanging off corridors and fixtures off rooms.
That shape was chosen because it is adversarial for greedy search in a specific,
realistic way: nearby goals cluster in rooms, but finishing a room before moving on
is exactly what h-add-guided GBFS fails to do reliably — which is visible in the
plan-length benchmark. See [benchmarks.md](benchmarks.md).
